# ADR-0006: サービス間の外部 ID を組織照合する（段階的・fail-closed）

- 状態: **proposed**（オーナー承認前。採択された決定ではない）
- 日付: 2026-10-21
- 決定者: 提案（本セッション）。採択はオーナー
- 上位規範: `Conforms-to: ADR-0004（テナント分離）`。MCDX-ADR の該当がある場合はそれを優先する
- 関連: #151（本 ADR の起案 Issue）、#139（作成者の偽装）、`docs/architecture/rbac-role-model.md`

## 背景

ADR-0004 は「各サービスは **自分の台帳** の `organization_id` を JWT の `org` で必ず絞る」ことを定めた。
しかし、サービスが **他サービスのレコード ID** を保存する経路（`project_id`、`document_id` 等）は
ADR-0004 の範囲外であり、**その ID が呼び出し元の組織のものか**は検証されていない。

現状の実測（2026-10-21、`services/*/src/models` と `src/schemas` の grep）:

| 外部 ID | 利用するサービス（重複なし） | 件数 |
|---|---|---|
| `project_id` | advanced, autonomous, bim, construction, document, erp, field-dx, gis, iot, maintenance, partner, platform, safety | **13** |
| `document_id` | advanced, document, vision | 3 |
| `equipment_id` | autonomous | 1 |
| `device_ids` | autonomous, platform | 2 |
| `model_ids` | platform | 1 |
| `reviewer_id` | advanced | 1 |
| `ledger_id` | erp | 1 |

この状態では、例えば自組織の `project_id` を装って他組織の案件に紐づくレコードを作成でき得る。
**越境の実害が確認されたわけではない**（各サービスは自分の台帳しか返さないため、参照しても
他組織のデータは読めないことが多い）。しかし「FK の存在だけを信じる」設計は、
将来の集計・横断検索・通知で組織境界を破る温床になる。

## 選択肢

| 観点 | A: 同期照合（内部 API） | B: イベント駆動の検証 | C: リスク受容（緩和策） | D: 段階的（推奨） |
|---|---|---|---|---|
| 仕組み | 保存時に相手サービスの内部 API へ問い合わせ、`org` 一致を確認 | イベントで参照整合性を後追い検証し、不一致を隔離 | ID は信頼し、表示・集計側で組織を再フィルタ | 高リスク ID から同期照合し、低リスクは B/C |
| 越境の防止 | ◎ 保存時に拒否できる | △ 一時的に不整合が残る | ✕ 保存時は防げない | ○ リスク順に閉じられる |
| 遅延 | ✕ 相手サービスの応答に依存 | ◎ 保存は速い | ◎ | ○ 対象を絞れば許容 |
| 可用性結合 | ✕ 相手停止で保存不可（fail-closed） | ○ 非同期 | ◎ | ○ 高リスクのみ |
| 実装コスト | 高（内部 API・認証・全サービス） | 高（イベント基盤・整合ジョブ） | 低 | 中 |
| 失敗時の挙動 | 404/403 で保存拒否 | 後追いで隔離・補正 | 越境が残る | 段階ごとに定義 |

**推奨: D（段階的）。** 理由:

1. 13 サービスが `project_id` を受けており、一括同期照合は可用性結合と実装コストが大きい。
2. まず **参照整合性が権限判断に効く ID**（`project_id`、`document_id`、`reviewer_id`）を同期照合し、
   `device_ids` / `model_ids` のような **表示・同期用の参照** は B または C に寄せる。
3. 失敗時は **fail-closed**（404/403）を原則とし、相手サービスの一時障害で保存できないことを
   運用上許容できる範囲から開始する（例: `project_id` は作成時に必須のため影響大 → 先にキャッシュ方針を決める）。

## 決定（案）

1. **外部 ID の台帳を作る。** どのサービスがどの外部 ID を、どの操作（作成/更新/参照）で受けるかを
   `docs/architecture/external-id-catalog.md` に列挙する（実装 Issue 1）。
2. **Phase 1**: `project_id` を保存する 13 サービスについて、作成・更新時に
   `construction` の内部 API（`GET /internal/projects/{id}?org=...` 相当）で組織一致を確認する。
   不一致・不在は **404**（存在を明かさない）。相手停止時は **503** とし、勝手に保存しない。
3. **Phase 2**: `document_id` / `reviewer_id` を同じ方式へ。`device_ids` / `model_ids` は
   参照時フィルタ（C）で開始し、必要になった時点で B へ移す。
4. **作成者・実行者は本文から受け取らない**（#139）。これは本 ADR と独立に全サービスで守る。
5. **キャッシュは Phase 1 では導入しない。** 導入する場合は TTL・失効・組織変更時の無効化を
   別 ADR で決める（古い許可を残さない）。

## 影響

- 保存経路のレイテンシが相手サービス依存になる（Phase 1 の対象のみ）。
- 相手サービスの障害が保存の失敗として表面化する（fail-closed）。可用性要件と衝突する場合は、
  対象 ID を絞るか、非同期の補償（B）へ切り替える。
- 既存データの遡及検証は別途必要（過去に保存された外部 ID の組織不一致件数を確認する）。

## 実装 Issue への分割（提案）

1. 外部 ID 台帳（`external-id-catalog.md`）の作成とレビュー
2. `construction` の内部 API（組織付き案件参照）と内部認証
3. `project_id` を受ける 13 サービスの Phase 1 適用（サービスごとに 1 PR）
4. `document_id` / `reviewer_id` の Phase 2
5. 既存データの不一致件数調査（読み取り専用 SQL）と是正方針
6. 回帰テスト（他組織 ID の作成拒否・相手停止時の fail-closed）

## 未決

- **本 ADR は提案であり、採択されていない。** 実装は採択後。
- キャッシュの可否、相手停止時の 503 を許容するかは運用判断。
- CSSP / MCIP など他リポジトリの外部 ID 参照は本 ADR の対象外（各リポジトリの ADR で扱う）。
